## Source Request
Build the minimal full-stack feature: members directory visible only to logged-in members. Backend scope: require auth on GET /api/members, GET /api/members/:id, GET /api/members/:id/details and return 401 when unauthenticated. Frontend scope: existing mobile members directory must not reveal data when unauthenticated; redirect to login or show explicit login prompt; handle backend 401 explicitly rather than generic load failure. Use real remote/main truth and real validation evidence only. Out of scope: RBAC/ACL expansion, field masking, unrelated refactors, write endpoints, schema/db changes unless setup proves absolutely required and scope is re-opened.

## Scoped Brief
Deliver the smallest full-stack change set that enforces authentication on the three existing member read endpoints and updates the existing mobile members directory flow so unauthenticated users do not see member data and receive explicit login-required handling, with backend 401 handled explicitly rather than as a generic load failure.
- GET /api/members returns 401 without valid auth.
- GET /api/members/:id returns 401 without valid auth.
- GET /api/members/:id/details returns 401 without valid auth.
- Existing authenticated behavior for those read routes remains functional.
- Existing mobile members directory no longer reveals member list/detail data to unauthenticated users.
- Mobile unauthenticated path explicitly routes to login or shows a clear login-required prompt.
- Mobile handling for backend 401 is explicit and not reported as a generic load failure.
- Suggested next step after scoping is Setup.

## Unknowns
- Whether the mobile members flow should prefer immediate redirect to `/login` or an in-screen login-required prompt as the primary UX; the source request allows either, so implementation should choose the smallest existing-path option.
- Whether any member detail mobile route currently fetches protected data independently and therefore also needs explicit unauthenticated handling to fully avoid disclosure.
- Which existing automated mobile validation path is runnable in this repo for the members/login flow, versus relying on targeted backend tests plus manual or E2E evidence during QA.

## Leader Assumptions
- `server/src/middleware/auth.ts` is the intended existing auth mechanism for protecting the target GET member routes.
- `mobile/app/login.tsx`, `mobile/app/utils/auth.ts`, and `mobile/app/members.tsx` are the existing mobile auth and members flow entry points to update, based on repo inspection.
- No schema/db change should be needed because the requested feature is access control on existing read routes and client behavior on existing screens.

## Out of Scope
- RBAC, per-field masking, role-based differentiation, or any ACL expansion beyond authenticated vs unauthenticated access.
- POST/PUT/DELETE member endpoint changes.
- New endpoints, new tabs/pages/workflows, or unrelated mobile/server refactors.
- Schema, Prisma, or database changes unless Setup produces hard evidence that current auth setup cannot satisfy the scoped request.
- Documentation-only polish that is not required for implementation or validation evidence.

## Risks/Blockers
- The mobile app currently calls `fetch` directly in `mobile/app/members.tsx` instead of the shared authenticated helper in `mobile/app/utils/api.ts`, so the frontend lane may require a slightly broader edit within existing mobile auth plumbing to make 401 handling correct.
- Existing backend tests around members routes appear to cover open access behavior today; auth enforcement will likely require test updates and careful preservation of non-target write-route behavior.
- There is repo evidence for a hidden `member-detail` route, so QA must confirm no unauthenticated disclosure remains through that existing flow if it consumes protected member APIs.

## Recommended Next Step
Setup
