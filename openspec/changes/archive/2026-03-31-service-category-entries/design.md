## Context

当前公共服务页面已有基础入口展示能力，但分类覆盖不完整，与需求草图存在差距。`docs/feature-service-category-entries.md` 已明确定义需要补齐的分类列表和验收标准。

本设计基于现有公共服务页面结构，仅补齐分类常量与展示顺序，不引入新的配置层或抽象层。

## Goals / Non-Goals

**Goals:**
- 补齐缺失分类入口：法律服务、金融服务、财税服务、工商服务、IT 技术、政务服务、HR 服务、产品服务、信息发布
- 统一分类名称与需求口径一致
- 统一分类展示顺序
- 对新增入口保持与现有页面一致的卡片/图标/文案展示风格，不重构现有样式体系

**Non-Goals:**
- 预约/申请/咨询流转能力
- 后台配置分类排序或开关
- 新增详情页/表单页
- 新增 API 或数据库变更
- 改动其他公共服务模块

## Decisions

### 1. 分类常量来源与存储方式
**决策**: 沿用现有公共服务页面的分类常量定义方式，在前端代码中以静态常量/配置数组形式维护。

**理由**:
- 当前项目无后台配置能力，静态常量是最小实现
- 便于 typecheck 与测试验证
- 后续如需后台化可独立开新 change

**替代方案**:
- 后台配置化 → 超出本次 scope，需新增 API 与管理界面
- 配置文件抽离 → 增加复杂度，当前无此必要

### 2. 分类展示顺序
**决策**: 按需求文档约定的业务顺序硬编码展示顺序。

**理由**:
- 需求已明确分类顺序是业务规则，不是用户可配置项
- 硬编码最简单，不易出错

### 3. 入口跳转行为
**决策**: 新分类入口的点击行为与现有占位入口保持一致（例如跳占位页或统一提示）。

**理由**:
- 本次只补入口展示，不补后端流转
- 保持用户体验一致

## Risks / Trade-offs

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 分类常量硬编码，后续调整需改代码 | 中 | 已在 proposal 明确后续后台化是独立 change |
| 新入口点击后无实际内容 | 低 | 与现有占位入口行为一致，已在非目标中明确 |
| 分类名称与业务口径未来可能变化 | 低 | 常量集中定义，调整成本低 |

## Migration Plan

### 部署步骤
1. 修改公共服务页面分类常量
2. 验证页面展示
3. 跑 typecheck
4. 验证既有入口行为未受影响

### 回滚策略
- Git revert 本次改动即可
- 无数据迁移，无 API 变更
