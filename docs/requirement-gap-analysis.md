# Yueqing Chamber — Requirement Gap Analysis

Branch baseline: `main`
Repo: `https://github.com/flyzorro/yueqing-chamber`

## Requirement assumptions confirmed

1. **商会成员** 和 **企业名单** 是两个独立模块。
2. **通讯录会员开放** 的规则是：**只有登录会员能看**。
3. **公共服务** 当前目标只是**展示服务分类入口**，暂不要求预约、申请、流转等能力。
4. **活动相册** 当前目标只是**纯展示图片**，暂不要求审核流或复杂管理。

---

## 已实现

### 1. 商会介绍
当前 `main` 分支已经具备基础商会介绍能力，包括：
- 商会简介
- 统计数据
- 快捷入口
- 最新动态

### 2. 商会成员（基础版）
当前已存在会员相关能力：
- 会员列表页
- 搜索
- 状态筛选
- 分页
- 下拉刷新
- 后端会员接口与基础数据模型

说明：当前更接近“会员列表 / 会员基础查询能力”。

### 3. 活动介绍（基础版）
当前已实现：
- 活动列表
- 时间地点展示
- 报名能力
- 后端活动列表/详情/报名接口

### 4. 公共服务（基础入口版）
当前已有公共服务页面，具备基础分类入口展示能力。
已覆盖到的方向包括：
- 法律
- 财税
- 融资
- 招聘/人才
- 商务考察
- 培训学习

## 部分实现

### 1. 商会成员
已实现基础会员列表与查询，但尚未体现更完整的成员体系，例如：
- 更完整的成员档案
- 更清晰的组织/分组结构
- 与通讯录权限联动的展示逻辑

### 2. 公共服务分类入口
如果目标只是“展示服务分类入口”，当前已经接近可用；但与需求草图相比，仍存在两个问题：
- 分类尚未完全覆盖
- 当前分类名称与业务口径未完全对齐

因此暂判定为**部分实现**。

### 3. 通讯录会员开放
当前已有会员列表能力，但还没有明确体现：
- 只有登录会员可见的权限控制
- 通讯录专门入口
- 登录态与字段可见性的明确规则

因此只能判定为**部分实现**。

## 未实现

### 1. 企业名单按行业分类
当前虽然已有独立企业名单模块，但未看到：
- 行业分类字段
- 按行业筛选
- 按行业分组展示
- 企业名录维度的独立分类页面

### 2. 公务员名单
当前未看到：
- 公务员名单独立模块
- 对应页面
- 对应数据模型
- 对应接口

### 3. 活动相册（纯展示图片）
需求已确认：活动相册只要求纯图片展示。
当前未看到：
- 活动相册页面
- 相册图片数据结构
- 图片展示逻辑
- 相册相关接口

### 4. 通讯录“仅登录会员可见”的明确实现
虽然已存在会员数据展示能力，但“只有登录会员能看”这个规则本身还未被明确落地为完整功能。

### 5. 公共服务缺失的分类入口
根据需求草图，当前尚未明确看到这些分类入口：
- 金融服务（完整分类意义上，不只是融资）
- 文旅
- IT 技术
- 政务服务
- HR 服务（完整模块意义上）
- 外包服务
- 信息发布

---

## 需求不清 / 后续可继续确认

以下问题虽然当前不影响本轮结论，但建议后续明确：

1. **企业名单** 是否只展示企业基础信息，还是还需要企业详情页。
2. **通讯录** 是展示所有会员联系方式，还是仅展示部分字段（例如姓名、公司、职位、电话）。
3. **活动相册** 是否需要按活动维度归档，还是一个统一相册入口即可。
4. **公共服务入口** 是否要求后台可配置排序和开关。

`main` 分支已经完成了一个**基础版商会 App** 的核心框架：

**后续说明**

### Package C — 通讯录仅登录会员可见
**目标**
- 明确把通讯录做成“仅登录会员可访问”的功能。

## Recommended execution order for Antfarm

如果要和 `feature-dev` 对齐，我建议执行顺序是：

1. **Package A** — 企业名单独立模块
2. **Package B** — 企业名单按行业分类
3. **Package C** — 通讯录仅登录会员可见
4. **Package E** — 活动相册（纯展示）
5. **Package D** — 公务员名单
6. **Package F** — 公共服务分类入口补齐

### 为什么这样排
- A/B 是一个自然连续链路，边界清晰，最适合先验证工作流。
- C 有权限判断，独立做更稳。
- E 范围相对清楚，适合中等复杂度功能。
- D 和 F 更偏信息架构/内容模块，放后面更合适。

## How to use this with feature-dev

给 antfarm 时，建议**一次只投一个 package**，不要把整份 gap 文档一次性塞进一个 feature-dev 任务。

### 推荐方式
- 一次一个 package
- 每个 package 明确：repo、branch、task、requirements、acceptance criteria
- 不把“企业名单 + 通讯录权限 + 活动相册”打包成一个任务

### 不推荐方式
- “把 gap 文档里所有没做完的都做了”

这样会让 planner 产出太多 stories，增加 setup/implement/verify 失败概率。
