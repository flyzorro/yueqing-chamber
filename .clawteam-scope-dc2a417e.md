## Source Request
Implement Package A from docs/requirement-gap-analysis.md for yueqing-chamber: build an independent company directory module. Add a distinct company-directory entry and a dedicated company list page that is clearly separate from the chamber members page semantics. Reuse existing data structures where appropriate, add only the minimal fields needed, and do not build company detail pages, admin management, or complex search/sort/recommendation. Acceptance: there is a distinct company-directory entry, the company directory is not the same page as members, the company list shows basic information correctly, existing members/activities/services flows are not broken, company-directory related tests pass, and typecheck passes with real evidence.

## Scoped Brief
This run should deliver the smallest verified slice needed to expose an independent company directory in the mobile app without changing the already-present company list data contract unless a concrete implementation blocker appears during Setup. Confirmed scope for this run is:
- add a distinct user-facing company-directory entry in the existing mobile navigation surface
- add a dedicated company list page/screen in mobile that is separate from the members page semantics, title, and UI copy
- connect that screen to the existing company list data source and render basic company list information already supported by the current model contract
- keep current members, activities, services, and profile flows working
- validate with real typecheck plus company-directory-focused tests/evidence available in the repo

## Unknowns
- Whether the distinct entry should live in the bottom tab bar, only on the home shortcut grid, or both is not explicitly specified by the source request.
- There is no discovered mobile test harness yet; whether company-directory validation will rely on existing server tests plus mobile typecheck/manual evidence or require adding a lightweight UI test is not yet confirmed.
- It is not yet confirmed whether the existing company fields (`name`, `industry`, `contactName`, `phone`, `address`, `logo`, `status`) are sufficient for the final UI layout without any minimal UI-only field mapping/formatting changes.

## Leader Assumptions
- Assume Package A can be completed as a UI-only delivery path because the repo already contains existing company-list server support, a `Company` Prisma model, fixture data, and passing server-side company tests.
- Assume “basic information correctly” means rendering a subset of existing list-safe fields from the current company-list response rather than introducing new backend fields or a company detail page.
- Assume preserving separation from members means the company directory must have its own page identity and user-facing labels, not just a filtered variant of the members screen.

## Out of Scope
- Company detail pages
- Admin CRUD or management behavior for companies
- Complex company search, sort, recommendation, or multi-dimensional filtering
- New backend codepaths, auth rules, schema migrations, or database redesign unless Setup proves the current company list contract cannot support the scoped UI
- Industry classification/browsing package work from Package B
- Any changes to activities, services, member details, or login flows beyond regression-safe navigation adjustments required by the new company-directory entry

## Risks/Blockers
- No existing mobile automated tests were discovered under `mobile/`; QA may need to rely on typecheck plus targeted verification evidence unless Setup finds another real UI validation path.
- The home screen and tab layout are both current navigation surfaces; choosing the wrong insertion point for the “distinct entry” could create review churn if product expectation differs.
- The existing backend already exposes companies independently, so unnecessary backend edits would increase regression risk without helping acceptance.

## Recommended Next Step
Setup: confirm current validation commands for `mobile` and `server`, verify the detached worktree state, and baseline the existing company-list/typecheck/test commands before launching two parallel implementation lanes (navigation/page lane and verification-support/regression lane within the allowed UI budget).
